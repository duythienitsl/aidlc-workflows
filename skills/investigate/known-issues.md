### Tour stuck at "full suite ready", HS deal stage never advances (LHP-2093)
- **Symptom:** ClickUp scan task sits at status "full suite ready"; the HubSpot deal stays on its prior stage (e.g. "Scan Booked"/`appointmentscheduled`) with no Close Date; no delivery email.
- **Systems:** Make scenarios 1361500 → 1361501; ClickUp; HubSpot. (Automation lives in Make, not the repo.)
- **Root cause:** Make **1361500** has a `BasicRouter` with no fallback route — Global Platform tasks whose tour link is only in the ClickUp *description* (not the `VT Property URL` / `Portal Link` form fields) match no route and are silently skipped, so the status never advances. Because the task never reaches "fsr email sent"/"fs complete", **1361501** (which only watches those statuses) never runs → deal stage never set to `5892159`.
- **Where to look:** Make `scenarios_get` 1361500 (module 86 router) + 1361501 (status filter `["fsr email sent","fs complete","booking completed"]`); ClickUp custom fields `VT Property URL`, `Portal Link`, `VT`, `Deal Id`; HS deal stage (`5892159` = Full Suite Sent). Team 355593 / org 886535.
- **Fix / status:** external — fix the Make 1361500 router (add a fallback / read the link from description). Not a repo change.
- **Example IDs:** Global Platform tours whose links live only in the description field.

### Duplicate "tour delivered" email on revisit bookings
- **Symptom:** Customer gets a second "your assets have been delivered" email when a **revisit** re-scan is delivered.
- **Systems:** HubSpot workflow 187350328; revisit deal records; revisit builders (api-platform + legacy).
- **Root cause:** The email is sent by HubSpot workflow **187350328**, which enrolls a deal at `dealstage=4516088` AND `email_sent_tourdelivery=false`. Its **only** revisit guard is `description DOES_NOT_CONTAIN ["vidsta","revisit","extended hosting"]` — but revisit deals **never write `description`** (api-platform `buildRevisitHubspotProperties` and legacy `API/API/Bookings/RevisitBooking` both omit it). The "revisit" signal lives only in `dealname`/`is_revisit_booking`/`revisit_type`, which the workflow doesn't inspect → guard passes → revisit gets the email. (HubSpot dedupes near-simultaneous identical sends, so you may see 2 enrollments but 1 delivered duplicate.)
- **Where to look:** `hubspot-get-workflow` 187350328 (guard); deal props `dealstage`, `email_sent_tourdelivery`, `is_revisit_booking`, `revisit_type`, `description`; associations typeId 451 (revisit↔parent). HubSpot only logs property history on a value change — a re-fire on an already-delivered deal leaves no footprint.
- **Fix / status:** durable fix is HubSpot-side (exclude on `is_revisit_booking=Yes` / revisit pipeline, not free-text), and/or ensure revisit deals don't enter stage 4516088 with `email_sent_tourdelivery=false`. Tracked under `docs/fix-revisit-gaps/`.
- **Example IDs:** deal 58373959250 (CAMP HILL); revisit deals 59159531164 + 59231105829 (delivered 28/05); contact marlini.patel@raywhite.com.

### Paid add-on order silently has no HubSpot deal (LHP-2185)
- **Symptom:** A paid add-on (e.g. a $660 Depreciation Schedule) never shows on the property's HubSpot deal — amount not increased, `depreciation_schedule_order` blank, no standalone "Add On" deal. Ops can't see/report the order.
- **Systems:** api-platform `payment.service.ts` (`processOrderAfterCheckout` → `createAddonHubSpotDeal`); HubSpot deals; Stripe; prod MySQL `additional_assets_orders_p`. (Confirm api-platform owns it: a `depreciation_form_submissions_p` row for the order = api-platform ran, not legacy.)
- **Root cause:** `createAddonHubSpotDeal` is wrapped in a catch that **only logs** (`payment.service.ts:1148` → `1165-1170`); on failure `hubspotDealId` is persisted `null` (`1220`) with **no retry and no alert** → a PAID order is orphaned. The standalone create (`payment.service.ts:1989`) lacks the booking-create resilience (`bookings.service.ts:3618/3676`), so a transient HubSpot error becomes permanent data loss. (NOT the LHP-2184 blank-field bug — there no deal is built at all.) **Admin no-payment orders are worst-hit:** when the creator is `LH_ADMIN` (or total $0), `payment.service.ts:337` routes past Stripe to `createOrderWithoutPayment` → `processOrderAfterCheckout` in-request (`:994`); no `checkout.session.completed` → the webhook backstop `processAddOnCheckoutBackstop` never covers them, so the single in-request attempt is the only chance. Tell-tale: `stripeSessionId` starts `session_without_payment_checkout_`.
- **Where to look:** `payment.service.ts:1148/1165-1170/1220/1989`; resilient reference `bookings.service.ts:3618`→retry `3676`. Find all affected: `SELECT id,tourIdString,finalAmount/100,createDate FROM additional_assets_orders_p WHERE paymentStatus='PAID' AND hubspotDealId IS NULL`. ClickUp `clickupId=null` on DS-only orders is by-design skip (`payment.service.ts:1180-1217`).
- **Fix / status:** open → `docs/lhp-2185-addon-order-no-hubspot-deal/`. Recommended: persist failure marker + scheduled reconciliation re-running `processOrderAfterCheckout` (idempotent) + Datadog alert; + make standalone create resilient; + backfill affected orders (human-approved prod write).
- **Example IDs:** order 1539 ($660 Depreciation, tour 34420 `Unit_3105-_19_Anderson_Street-_KANGAROO_POINT_QLD_4169`, deal `58439358054`, form submission 101, `stripeSessionId=session_without_payment_checkout_1781143170694`, createdBy 5617 = sharon@littlehinges.com.au LH_ADMIN) — Sharon's, admin no-payment; order 1493 ($35 virtual staging). ### Insights metric formulas & DynamoDB partition-key gotcha (reference)
- **Symptom:** Insights numbers look wrong/misaligned, or a DynamoDB query returns false "No results".

## Bookings / Acuity availability

### `/acuity/available-slots` returns no fixed slots — availability parked on Overflow / normal calendar Closed for the type
- **Symptom:** For a given appointment type (region), `GET /acuity/available-slots?acuityAppointmentId=<typeId>` (openhouse booking / postcode lookup) returns **no fixed `times`** — at most flexi-only days — even though the Acuity admin day-view shows open white blocks on the technician calendar. Reported for type `52795664` "Brisbane Greater West" (postcode 4077), 2026-07.
- **Systems:** api-platform `AcuityController.getAvailableSlots` (owns the endpoint) + Acuity config (the actual fault). Not legacy.
- **Root cause:** The endpoint sources fixed `times[]` from **NORMAL calendars only**; `"…overflow"`-named calendars only set the per-day `flexi` flag (LHP-2221) and `"…production"`-named calendars are dropped entirely (`.toLowerCase().includes('production')`). If, in Acuity, the type's **only technician (normal) calendar has no per-type hours** (its availability *group* for that calendar is set **Closed**) while all real capacity sits on the region's **Overflow** calendar, the union of fixed times is empty → no fixed slots. The white blocks in the admin view are the calendar's hours for a *different* appointment-type group (e.g. "Brisbane Inner"), not for this type. **Not a code bug — Acuity configuration.**
- **Where to look:** `api-platform/src/acuity/acuity.controller.ts:119-127` (production filter), `:191-202,237-248,341-357` (overflow→flexi only, drop empty days); `bookings/helpers/calendar-overflow.ts:17-19` (`includes('overflow')`); test lock `acuity.controller.spec.ts:326` ("does not query the ZZZZ Production calendar"). **Verify read-only via Acuity GET** (creds in `api-platform/.env`, `ACUITY_USER_ID=32072881`): `GET /appointment-types` → type's `calendarIDs`; `GET /calendars` → names; `GET /availability/dates?appointmentTypeID=<type>&calendarID=<normalCal>&month=YYYY-MM` (empty = normal calendar has no per-type hours) vs `&calendarID=<overflowCal>` (populated = capacity is on Overflow). In the Acuity UI: the calendar's **availability Group** holding that type is set **Closed**.
- **Fix / status:** **external (Acuity console)** — open working hours for the type's group on the technician calendar (or move the type onto a technician calendar that has hours). Sibling type in the same region that *works* is the reference (Brisbane **Pro 3** `56463558`, normal calendar Bris 3 - Noah `6073377`, has hours). ## Infra / Deployment (ECS / ALB)

### dev api-platform ECS deploy stuck — tasks killed by ALB health check before boot completes
- **Symptom:** On **dev**, every new `dev-api-platform` ECS task reaches `RUNNING` then is stopped with `Task failed ELB health checks in (target-group .../dev-api-platform-tg)` and container `Exit code: 143`. Deployment loops for hours (`IN_PROGRESS`, many "failed tasks"); dev stays up because the previous task def keeps serving.
- **Systems:** AWS ECS/Fargate + ALB target group (the fault) + api-platform NestJS boot path (`docker-entrypoint.sh` → `prisma migrate deploy` → `node dist/main.js`). NOT an app bug, NOT legacy.
- **Root cause:** ECS service `healthCheckGracePeriodSeconds = 0` combined with ~40–80s app cold-start (entrypoint runs `prisma migrate deploy` before Nest init). ALB target group (interval 30s, unhealthy threshold 2, no grace) accrues 2 connection-refused checks during boot — the app isn't listening yet — and marks the target unhealthy ~40–70s after registration, before it can pass one check. ECS kills the task; `minimumHealthyPercent=100` keeps the old task alive so the new deployment loops forever. `exit 143` = ECS-sent SIGTERM (not an app crash). The "runs ~5 min then SIGTERM" is just ~300s ALB connection draining after the target was already declared unhealthy.
- **Where to look:** `describe-tasks` → `stoppedReason`, `exitCode 143`, `healthCheckGracePeriodSeconds`. CloudWatch `/ecs/dev-api-platform` stream `ecs/api-platform-container/<taskId>` → confirm `App is running on host http://0.0.0.0:3000/api/api-platform` + `Bootstrapped successfully` (app booted fine). Correlate ECS service events (`registered targets` → `is unhealthy`) with the log's listen time — register→listen gap ~40–60s > the 2×30s unhealthy window. Target group `dev-api-platform-tg` path `/api/api-platform`, matcher 200. Boot cost: `api-platform/docker-entrypoint.sh` (migrate before start). Ruled out: subnet/SG (fails span all 3 subnets; a failed task shared the healthy task's subnet), health-endpoint code (`main.ts` setGlobalPrefix + health unchanged between builds; live app returns 200 on `/api/api-platform`).
- **Fix / status:** **external (Terraform infra, not this repo)** — set `aws_ecs_service.health_check_grace_period_seconds` to ~120–180s on `dev-api-platform-service` (mirror to prod). Quick unblock: set grace 120s + force new deployment. Long-term hardening (repo, via `/write-prd`): move `prisma migrate deploy` out of the per-task entrypoint into a one-shot pre-deploy step. Infra repo ownership: `docs/api-platform-infra-terraform-ownership/`. Tracked under `docs/dev-api-platform-ecs-deploy-healthcheck-stuck/`.
- **Example IDs:** deploy of image `f5f55ea` (task def `dev-api-platform:281`, merge of `bug/LHP-2234` into `dev`), 2026-07-14; failed tasks `1f02c3518…`/`6623c2ec…`/`6ad73857…`; healthy holdover task def `278` (image `8b28a91`) at `10.0.20.129`; cluster `dev-api-platform-cluster`, account `686865765255`, ap-southeast-2.

## Environment caveats (not bugs, but common red herrings)

### UAT data is in the dev DB; FE ships via the `uat` branch
- UAT FE (`uat.platform.littlehinges.com`) → **dev** api-platform (`https://dev-api.littlehinges.com/api/api-platform`) → **dev** MySQL. Don't hunt a UAT repro in the prod DB.
- FE fixes reach UAT only after merging into the **protected `uat` branch** (feature branch → MR → uat → Vercel rebuild). A "still broken" UAT is often a stale deploy — check the last uat deploy time vs the merge, redeploy + hard-refresh before assuming the fix is wrong.
